Independent review of the completed cache-capacity comparison
2026-10-18 — research_refresh — CPU and saved evidence only

Accepted within the frozen, finite workload. Raising the existing HotRows cache
budget from 256 to 1,024 MiB per table reduced geometric-mean prefill latency by
10.0623% and whole-request latency by 9.1136%. It required approximately 1.5 GiB
more retained cache memory. Eight of 24 measured comparisons regressed, and both
warmups were slower. This supports a workload-dependent capacity tradeoff; it
does not establish an unconditional improvement or authorize a serving change.

The denominator is the actual frozen v3 implementation, already using the
stabilized dependency cone, DSpark correction, 64 MiB prefetch budget and existing
HotRows cache. The candidate changes the reviewed cache budget ceiling and its
matching messages. It introduces no new cache algorithm or arithmetic. Credit
for HotRows remains with its attributed upstream source. This result must not be
added to or multiplied by the earlier native64-versus-v3 result.

Design and observed latency

Four fresh model processes ran in 256 → 1,024 → 1,024 → 256 MiB/table order. Each
started with an empty row cache and ran one 16K warmup followed by the same 12
measured requests, preserving cache history within that process. Every request
used fresh KV state and generated 128 outputs. The 24 measured comparisons are
two repetitions of 12 existing cases from four corpora, not 24 independent
workloads. Matching inputs, seeds and order were frozen before measurements.
OS/file caches were retained across processes. This is block-level ABBA balance,
not adjacent per-request interleaving; it cannot eliminate storage, thermal or
time trends. These corpora were reused from earlier local qualification.

Sixteen pairs were faster and eight slower for all three metrics. Prefill

The last stratum is only one Moby Dick input repeated twice, with one regression.

History matters in the observed results. The first measured use of each corpus
within a process was 2.35% slower in aggregate (8 comparisons, 3 faster); later
uses were 15.69% faster (16, 13 faster). This additional descriptive split is
confounded by the fixed request order and input lengths; it is not an isolated
causal estimate of reuse. The first measured request of the process was 1.48%
slower across its two comparisons. The two separately reported warmup pairs both
regressed: prefill 11.5249 → 14.0672 s, or 22.06% more time. Four model loads took
23.30–24.29 seconds and are excluded from generation timing.

Logical reads, physical reads and memory

Across measured requests, unique-query hits rose from 9,840,900/36,596,946
(26.89%) to 15,038,816/36,596,946 (41.09%). Miss rows fell from 26,756,046 to
21,558,130. At the actual 160 bytes per selected packed row, selected native
payload fell 19.43%, from 4,280,967,360 to 3,449,300,800 bytes. Duplicate elision
was identical, and every same-budget logical counter trajectory reproduced
exactly in its second fresh process. All these counters include generation,
not only prefill.

Separately, measured process physical-read counters totaled 641.63 → 551.09 GiB
(14.11% less). These are not the packed-row byte counts or an Engram-only SSD
measurement. Six larger-cache requests read more physical bytes; two of those
were faster anyway. Conversely, several slower requests read fewer bytes. The
records do not identify a single cause for each latency change.

Maximum retained cache allocation was 536,870,912 versus 2,147,483,584 bytes
(512 MiB versus 2 GiB minus 64 bytes). Only one cache-owning model process ran at
a time; there is no uncounted inactive cache bank. Model, temporary gather/merge,
prefetch and other allocations are additional. Sampled maximum process footprint
was 216.348 versus 217.944 GiB, and minimum system available memory was 19.089
versus 18.278 GiB. These maxima occur in potentially different requests, so their
1.596 GiB difference is not an isolated allocation measurement. Existing swap
peaked at 1.510 GiB. Neither end-minus-start nor peak-minus-start swap increased
in the recorded samples, including all four loads, four warmups and 48 measured
requests. Sampling cannot exclude excursions between observations.

Independent evidence checks

The unchanged frozen archive validator and analyzer were rerun, and their report
reconciled with the accepted root analysis. Separate arithmetic recomputed paired
geometric means, counters and resource totals. All five archived source snapshots
were hash-checked, with 1,745 entries each. All 104 pre-enrichment and observed
request backups were hash-checked and associated with their actual job, worker,
input and final record. Sources and evidence were unchanged after the audit.

All 3,072 measured output positions and 1,218 functional MTP cycles matched
between budgets, including output text, proposal/acceptance decisions and emission
accounting. Warmups additionally matched 256 output positions and 84 cycles.
All 52 requests completed 128 outputs: 6,656 total generated positions across
both arms. Complete request traces account for 264 cone chunks, 264 successful
DSpark appends and 792 stage pads, with every required shape correction checked.
Timed requests contain no full-state archive or extra probe. These observed
generation matches are not a new full-state, arbitrary-input or model-quality
proof, and no separate decode-speed claim follows from the prefill result.

Actual model child PIDs 89898, 90085, 90332 and 90589 exited with code zero.
Each worker drained, native model cleanup completed, hooks and sources were
restored, both tables closed, and retained row memory returned to zero before
